## 4. 问题与不足（困难）
- 遇到的问题：
  - 一开始为了课堂可演示加入了离线 fallback 和 mock 数据，后来需求改为每一步必须基于 LLM，需要再清理执行路径。
  - LLM 生成的 plan schema 不稳定，出现过 `type: studyplan_skill`、Hint step 缺输入字段等问题。
  - Flask 进程曾经用 `OLLAMA_OFFLINE=1` 启动，导致页面一直显示 LLM 不可达。
- 产生原因（知识、时间、沟通、执行等）：LLM 输出不是强约束结构，且开发过程中环境变量和服务进程状态容易残留。
- 影响（效率、质量、进度）：调试时间增加，需要多次验证真实 LLM、Planner normalizer 和 Executor 输入组装。

## 5. 核心反思（最重要）
- 这次最值得复盘的一件事：LLM Planner 不能只靠 prompt 约束，还需要在代码层做 schema normalizer 和错误显式化。
- 如果重来一次，我会怎么做：先明确“是否允许离线兜底 / mock 数据”，再设计失败策略，避免后期从 fallback 模式切换到 LLM-only 时重复修改。
- 我学到的关键原则（1-3条）：
  - Planner 负责决策，Executor 负责执行，Skill 不应该偷偷调用 Tool。
  - LLM 输出必须验证和规范化，但不能用本地规则替代 LLM 决策。
  - 真实工具、Memory、LLM 的失败要显式暴露，不能用假数据掩盖。
